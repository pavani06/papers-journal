# Compile by Training: Turning Natural-Language Specifications into Local Neural Functions

**Sumário de ação**: Direção de arquitetura, não receita imediata: o harness consome modelos só por API e não tem estágio de treino local, então nada vira artefato compilado hoje. O aproveitável agora é taxonômico: separar chamadas de deliberação das que são transformação semântica repetida (papers-journal já pratica a divisão fuzzy/exato que o paper valida), e medir recorrência antes de qualquer decisão futura de compilação.

## Afirmação central

Uma especificação em linguagem natural pode ser compilada, num build de ~1 minuto com supervisão sintetizada por teachers, numa pequena função neural (LoRA sobre intérprete Qwen3-0.6B congelado) que roda localmente, sem chamar os teachers, e se armazena, versiona e compõe como software ordinário.

## Mecânica passo a passo

`Cobertura: html-complete` (HTML de 146,6 kB recuperado integralmente após truncamento do fetch; fim do documento verificado: Apêndice E encerrado + rodapé LaTeXML; seções 1-9, referências e apêndices A-E lidos)

1. **Especificação**: desenvolvedor descreve uma função texto-para-texto em linguagem natural. Interface: `p_s = Compile(s)`, `ŷ = Run(p_s, x)`.
2. **Supervisão sintetizada**: teachers (GPT-5.4-mini + GPT-5.5, mistura 2:1) geram pares (x, y) em JSON estruturado; o compilador valida cada resposta e rejeita lotes malformados ou incompletos antes de liberar exemplos para o treino.
3. **Especialização**: intérprete compartilhado congelado (Qwen3-0.6B quantizado); cada função é uma LoRA rank 64 alpha 16 mais um scaffold (prompt template com placeholder para o input). Warm start do compilador amortizado do PAW (predição em um forward pass, segundos), refinado por 100 steps (batch 48, decaimento cosseno) sobre os pares sintetizados.
4. **Empacotamento**: o artefato `.paw` carrega adapter, scaffold, spec original e metadados do intérprete; armazenável, versionável, componível. No runtime, o SDK combina input novo com scaffold + adapter e roda o intérprete; inputs futuros não vão para o serviço nem para os teachers. A compilação, porém, é hospedada: a spec viaja para o serviço PAW e para as APIs de teacher.
5. **Compilação interativa**: streaming path sobrepõe síntese e treino (o treino começa com o primeiro batch e só bloqueia se alcança a síntese); coordenação por fila persistente de jobs + workers GPU, com cache de saídas de teacher reusado entre jobs; a UI trata compilação como build de fundo que persiste entre navegação e reload.
6. **Aplicações**: paw-helper (30 programas compilados, 28 em roteamento vivo, um backend servindo 4 sites; funções compiladas decidem o fuzzy, código ordinário faz retrieval BM25, cache e branch); Avatar Director (programa neural emite DSL de ações, o browser valida e executa); tradutor bidirecional English-Claudish (um adapter por direção).

## Evidência e resultados

- Comparação principal (Fig. 4): na FuzzyBench-Hard, LEM médio 0.224 (compilador rápido do PAW) para 0.836 (compile by training), +0.612 absoluto, ao custo de 50.9 s contra 3.5 s de compilação. Condição: FuzzyBench-Hard é o subconjunto selecionado de specs em que o compilador rápido produziu zero exact matches; seleção adversarial ao baseline, não amostra do benchmark completo. O 83.6% não descreve acurácia no benchmark inteiro e o ganho não se extrapola para tarefas em que o fast compiler já acerta.
- LEM é a fração de predições que um juiz LLM (GPT-5.5) considera semanticamente corretas, dadas spec, input, referência e predição; juiz validado contra 128 rótulos dos autores: acc 0.977, κ 0.946, FPR 0.025, FNR 0.023 (Tabela 3). A margem de erro do juiz (~2%) é da ordem dos deltas menores da Tabela 1; sem IC ou teste de significância reportados.
- Sweeps em development specs (Tabela 1): mistura 2:1 mini/GPT-5.5 eleva LEM de 0.746 para 0.851 (3600 pares únicos repetidos até 6400 exemplos, batch 64 fixo); scaling de dados 1440/2400/3600/7200 pares únicos: 0.821/0.836/0.836/0.866, isto é, platô entre 2400 e 3600 com ganho retomando só em 7200.
- Latência medida no lançamento do serviço (maio 2026): cold compile de uma spec representativa em 50.9 s (B300), 68.2 s (H200), 99.2 s (RTX); teste de carga com 4 jobs concorrentes, espera média em fila 1.01 s. Amostra pequena, hardware específico, sem curva de carga além de 4 jobs.
- Avatar: 43 de 44 instruções de validação hand-authored produziram a estrutura de ação esperada. Amostra minúscula, escrita pelos próprios autores, sem avaliadores externos: evidência de demonstração, não estimativa robusta de taxa de erro.
- Claudish: 100.747 traduções bem-sucedidas entre 22/08 e 02/09/2026. Métrica de uso do serviço, não de correção; nenhuma acurácia de tradução é reportada para a demo.

## Limitações e riscos

- Declaradas (§9): supervisão sintética herda erros dos teachers; aplicações que exigem correção garantida devem validar saídas ou manter caminhos de controle determinísticos; sem user studies sistemáticos.
- Suspeitadas na leitura: (a) o runtime "local" exige o intérprete compartilhado (0.6B quantizado) presente no cliente, a função não é autossuficiente; (b) a compilação é serviço hospedado, então o build depende do serviço PAW e das APIs de teacher, justamente a dependência externa que o método remove do runtime, não do ciclo de vida; (c) a validação de lotes rejeita malformados, mas não há verificação independente da correção semântica dos pares sintetizados; (d) a dificuldade em FuzzyBench-Hard é definida pelo fracasso do baseline, então o ganho é por construção medido onde o baseline é pior.
- Sobre o título: "Local Neural Functions" é preciso quanto ao runtime, mas o compilador não é local; e "specifications" cobre funções texto-para-texto fuzzy, não especificações arbitrárias.

## Teses transferíveis

1. Taxonomia de chamadas LLM: separar deliberação (curadoria, julgamento contextual) de transformação semântica repetida (classificar, normalizar, extrair, com spec estável). Só a segunda família é candidata a artefato compilado, e a decisão começa por medir recorrência, não por compilar.
2. Divisão de trabalho fuzzy/exato: componentes neurais para decisões fuzzy; código ordinário para retrieval, cache, validação e branch de controle. Padrão que o paper valida em produção (paw-helper) e que o ecossistema já pratica.
3. Validação como etapa de build: saída de modelo entra no pipeline só depois de validada estruturalmente, e defeito de aquisição (truncamento, lote malformado) é devolvido como fato auditável, nunca escondido atrás de flag de sucesso.
4. Reuso de trabalho entre jobs: cache de saída de modelo selado, com proveniência, permite re-render e re-execução sem nova chamada, e alimenta memória entre execuções; a parte cara é a chamada, e é ela que se protege primeiro.
5. Economia do build: compilação de ~1 min compensa quando a função roda milhares de vezes (100k+ na demo Claudish); abaixo disso, chamada por API ganha. O ponto de equilíbrio é função da frequência de uso, não da elegância do método.

## Veredito do paper

Vale destilar como direção de arquitetura, não como receita: o método exige estágio de treino local (GPU, LoRA, intérprete dedicado) inexistente num harness que consome modelos só por API. O que fica hoje: (1) a taxonomia deliberação vs transformação repetida como critério de triagem de skills e chamadas, (2) validação empírica do padrão fuzzy/exato que já governa o jornal de papers, (3) o lembrete de que artefato versionável supera prompt solto quando a função é estável e frequente.
