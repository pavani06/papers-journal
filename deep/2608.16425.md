# ParaTempo: Efficient Parallel Reasoning via Temporal Confidence

[HF](https://huggingface.co/papers/2608.16425) · [arXiv](https://arxiv.org/abs/2608.16425) · texto completo
## O que o paper afirma

ParaTempo é um controller para **parallel reasoning** que tenta gastar menos tokens e reduzir latency sem perder muito da acurácia de self-consistency com várias amostras.

A tese central: em vez de deixar `K` branches raciocinarem até o fim e só depois votar, dá para controlar cada branch durante a geração usando um sinal local de convergência chamado **temporal confidence**.

O mecanismo é:

1. Rodar vários branches em paralelo.
2. A cada `τ` tokens, interromper logicamente cada branch e fazer um **probe intermediário**: forçar o modelo a dar uma resposta provisória a partir do prefixo atual.
3. Transformar os top-`L` candidatos em buckets normalizados de resposta.
4. Manter uma janela deslizante das últimas distribuições de resposta daquele branch.
5. Calcular:

   ```text
   temporal_confidence = exp(-entropy(distribuição_agregada))
   ```

   Se as respostas provisórias recentes estão concentradas no mesmo bucket, a entropia cai e a confiança sobe.

6. Usar esse sinal para controlar o ciclo de vida dos branches:
   - **prune**: matar branches com baixa confiança temporal;
   - **retire**: parar branches que já parecem estabilizados, mantendo seu voto;
   - **fork**: reaproveitar budget liberado criando novo branch a partir de um prefixo promissor;
   - **global early stop**: parar tudo quando o voto ponderado por confiança estiver concentrado o suficiente.

A novidade prática não é a fórmula de entropia. É juntar quatro operações úteis num controller assíncrono: pruning, retirement, forking e early stopping, todos guiados por uma noção temporal de convergência de resposta.

## Como sustentam

A avaliação é em benchmarks de raciocínio fechado:

- AIME 2026
- HMMT November 2025
- HMMT February 2026
- GPQA Diamond

Modelos:

- Qwen3.5-35B-A3B
- GPT-OSS-20B

Baselines:

- zero-shot
- self-consistency `SC@16`
- ESC, early-stopping self-consistency
- SAC, answer convergence
- DeepConf
- Parallel-Probe

Métricas:

- acurácia
- wall-clock latency
- total generated tokens
- sequential generated tokens, como aproximação do critical path

O setup usa `K=16` branches, `τ=500` tokens por probe, `top-L=20`, budget máximo de 16.384 tokens por trajetória, vLLM em uma A100 80GB. Os resultados são média de quatro runs.

O que a evidência sustenta bem:

- O sinal temporal é menos volátil que entropia/perplexity de token e que confiança instantânea de resposta.
- Em tarefas de resposta fechada, a agregação temporal de probes parece um sinal melhor para decidir se um branch estabilizou.
- ParaTempo reduz custo contra `SC@16`: o paper reporta reduções de latency na faixa de ~22–32% e tokens na faixa de ~18–30%, dependendo do modelo.
- As ablations fazem sentido: remover pruning aumenta custo; remover retirement piora custo e acurácia; remover forking economiza mais, mas perde acurácia.

Onde a evidência é fraca:

- A avaliação é toda em **QA/raciocínio fechado**, principalmente matemática e múltipla escolha. Não há agentes de código, ferramentas, repositórios, side effects, testes, nem long-horizon task execution.
- ParaTempo nem sempre preserva a acurácia de `SC@16`. Exemplo: em Qwen, AIME cai de 87.5 para 83.3; em GPT-OSS, AIME cai de 90.0 para 86.7. A alegação correta é “boa troca custo/acurácia”, não “mantém a mesma acurácia”.
- Benchmarks como AIME/HMMT têm poucos exemplos; quatro runs ajudam, mas faltam intervalos de confiança ou testes estatísticos.
- O custo dos probes não fica totalmente claro em termos operacionais. Em self-hosted vLLM com KV cache, pode ser barato. Em API externa, pode custar caro porque você talvez precise reenviar contexto ou não tenha acesso a logprobs/top-k.
- Os hyperparams são numerosos: `W`, `X`, `N_warm`, `q_prune`, `θ_retire`, `γ_ES`, `τ`, `K`, `L`. O paper mostra uma configuração padrão, mas não prova robustez ampla fora desse regime.
- A comparação de latency depende muito do runtime. Uma A100 com vLLM e 16 branches paralelos não é o mesmo ambiente de um harness usando modelos de terceiros, rate limits e billing por request.

## O que dá para aproveitar

A ideia aproveitável é tratar execução paralela de agentes como **controle online de branches**, não como “dispare N tentativas e vote no fim”.

Para um harness de agentes, a transplantação mais útil seria esta:

### 1. Probes periódicos de estado

A cada bloco de trabalho — por exemplo, a cada N mensagens, N tool calls, N arquivos inspecionados ou N tokens — peça a cada branch um estado provisório normalizado.

Exemplo para agente de código:

```json
{
  "hypothesis_bucket": "bug_in_parser_normalization",
  "proposed_fix_bucket": "change_normalize_path_before_lookup",
  "confidence": 0.72,
  "evidence_refs": ["trace:17", "file:src/parser.ts:88", "test:repro_fail"]
}
```

Se o modelo/API der logprobs sobre respostas curtas e normalizadas, melhor. Se não der, dá para usar self-reported confidence, mas isso é bem mais fraco que o sinal do paper.

### 2. Agregar no tempo, não decidir por uma medição isolada

Mantenha uma janela das últimas respostas provisórias por branch.

Algo como:

```text
g_branch(bucket) = média das probabilidades dos últimos W probes
temporal_conf = exp(-entropy(g_branch))
top_bucket = argmax(g_branch)
top_mass = max(g_branch)
```

Isso evita matar ou promover um branch só porque ele teve uma resposta confiante em um ponto intermediário.

### 3. Separar lifecycle de branch

No harness, implemente estados explícitos:

- `active`: continua trabalhando;
- `retired`: parou, mas mantém voto/evidência;
- `pruned`: descartado por baixa convergência ou baixa utilidade;
- `forked`: novo branch derivado de um checkpoint promissor.

Isso conversa bem com worktrees, subagentes e trilha de evidência.

### 4. Retirement é mais seguro que early final answer

Para produção, o melhor uso não é “parar tudo porque o modelo está confiante”. É:

> “este branch já convergiu; pare de gastar nele, preserve sua evidência e deixe outros branches continuarem.”

Isso reduz custo sem transformar confiança interna em critério final de correctness.

### 5. Forking pode virar política de alocação de subagentes

Quando um branch ruim é podado, em vez de abrir uma nova tentativa do zero, fork a partir de um branch com:

- boa convergência temporal;
- evidência concreta;
- plano ainda não totalmente explorado;
- worktree limpo ou checkpoint reproduzível.

Para agentes de código, isso pode ser: clonar o worktree de um branch promissor antes da edição final, variar a estratégia de patch ou variar a bateria de testes.

### 6. O voto final precisa ser evidência-ponderado, não só confiança-ponderado

O paper vota por resposta ponderada pela massa top-1. Em agente de software real, isso é perigoso. Melhor ponderar por algo como:

```text
score = temporal_confidence
      * evidence_quality
      * verification_pass_rate
      * reproduction_strength
      * independence_penalty
```

Ou seja: temporal confidence é um sinal de convergência, não de verdade.

## Armadilhas

### Precisa de answer buckets

O método funciona porque AIME, HMMT e GPQA têm respostas normalizáveis: número, opção, resposta curta.

Em tarefas abertas de software, “a resposta” pode ser:

- um patch;
- uma explicação;
- uma hipótese de causa raiz;
- uma sequência de ações;
- um conjunto de arquivos;
- uma decisão de rollback;
- um plano de migração.

Sem uma taxonomia de buckets, a entropia vira ruído. Você teria que definir buckets operacionais: causa raiz, tipo de fix, arquivo-alvo, próxima ação, status de verificação etc.

### Convergência não é correção

Um branch pode estar consistentemente errado. Temporal confidence mede estabilidade da crença, não validade.

Isso é especialmente perigoso com forking: se o branch errado tem alta confiança, o controller pode criar mais branches derivados dele e reduzir diversidade real.

### Logprobs e probes podem não estar disponíveis

O paper depende de obter top-`L` candidatos e logprobs a partir de um prefixo intermediário com um sufixo tipo:

```text
</think> Final answer:
```

Em modelos de terceiros, você pode não ter:

- acesso a hidden reasoning;
- logprobs em modelos reasoning;
- top-k suficiente;
- controle de prefixo;
- KV cache reutilizável;
- custo baixo para probes frequentes.

Se você tiver que reenviar todo o contexto a cada probe, a economia pode desaparecer.

### Warmup é caro

A configuração padrão usa:

```text
τ = 500 tokens
N_warm = 15 probes
```

Ou seja, o controller só começa a intervir depois de algo como 7.500 tokens por branch. Para tarefas curtas ou agentes com tool calls caros, isso é tarde demais.

Em produção, você provavelmente precisaria adaptar `τ` para unidades de trabalho: “após ler arquivos críticos”, “após executar repro”, “após primeiro patch”, não apenas tokens.

### Forking em agentes com side effects é difícil

Forking prefixo em raciocínio puro é simples. Forking agente real exige isolamento:

- worktree separado;
- filesystem sandbox;
- banco/test environment isolado;
- tool logs versionados;
- capacidade de replay;
- limpeza de side effects.

Sem isso, o branch forkado herda estado ambíguo e a trilha de evidência fica contaminada.

### Pode degradar diversidade

Selecionar donor por maior temporal confidence favorece o branch mais convicto, não necessariamente o mais promissor. Em problemas onde a primeira hipótese forte costuma estar errada, isso aumenta mode collapse.

Uma política mais segura em produção deveria misturar:

- confiança temporal;
- diversidade entre hipóteses;
- cobertura de arquivos/áreas;
- evidência independente;
- resultados de teste diferentes.

### Latency do paper não transfere automaticamente

Os ganhos foram medidos em uma A100 com vLLM. Num harness usando APIs externas:

- chamadas paralelas podem bater rate limit;
- cancellation pode não economizar billing;
- probes podem ser cobrados como requests extras;
- fork pode exigir reenviar contexto completo;
- tool calls dominam latency, não tokens.

Então o número “20–30% de economia” não deve ser importado diretamente.

### Não é benchmark de agente

O paper não mostra:

- edição de repositório;
- execução de testes;
- uso de ferramentas;
- recuperação de contexto;
- falha silenciosa;
- verificação independente;
- tarefas multi-sessão;
- custo de observabilidade.

Para o perfil do leitor, isto é um paper de **controller de inferência paralela**, não de agente de software.

---

## Veredito

Vale deixar no radar e talvez prototipar a ideia de **temporal confidence como sinal de lifecycle de branches**. A técnica é simples, compatível com harness de agentes e conversa diretamente com pruning, retirement e forking.

Não dá para adotar os números do paper como promessa de produção. A evidência é boa para raciocínio fechado com respostas normalizadas; para agentes de código, o ganho depende de você criar buckets úteis, probes baratos e gates de verificação que impeçam “convergência errada” de virar decisão final.
