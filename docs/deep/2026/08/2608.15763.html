Training Agents to Evolve with Their Harness: TaoLive Digital Avatar Agent Technical Report

Sumário de ação: Não treinamos pesos, então a técnica central (HAT) não se aplica diretamente — mas HSA destila-se como método de teste: suíte de regressão que re-executa a mesma tarefa sob perturbações nominais (renomear skill, schema equivalente, reordenar prompt, variar hook) para expor dispatch acoplado a rótulo frágil. Aplicar agora como invariantes de consistência nominal em agent-skills, teste de propriedade de superfície em scripts, e sistematização proativa da lição de gate pareado em sisyphus-runtime.

Afirmação central

O harness de um agente (skills, ferramentas, prompts, hooks) deve ser tratado como distribuição variável — perturbada durante o treinamento via Harness-State Augmentation — para que o modelo aprenda a interpretar o harness corrente em vez de memorizar rótulos e templates de uma configuração fixa.

Mecânica passo a passo

Leitura do HTML v3 (seções 1-3.3 na íntegra antes do truncamento do fetch; seções 4-6 e apêndices capturados via abstract e sumário estrutural).

  1. Arquitetura Harness Agent (seção 2): separação entre policy model (compacto, congelado, lento de mudar) e harness state h = (S, T, P, K) — Skills ativas (módulos Markdown versionados com metadados YAML e diretivas), Tool registry (schemas e descrições), system Prompt pipeline (instruções montadas dinamicamente), Hooks (validação de input, parâmetros, formato, retry). O harness evolui por Harness Evolution: loop humano-no-ciclo Diagnose → Confirm → Edit → Evaluate → Regression Check, mudando comportamento de negócio em horas sem retrain.
  2. O dilema (seção 1): modelos grandes generalizam zero-shot para harness mutável, mas a latência viola o tempo real (DeepSeek-V4-flash com mediana > 11s no cenário deles); o modelo compacto necessário para a latência precisa de treino de domínio, e SFT sobre harness fixo produz surface-form overfitting — casar skill por similaridade de string, escolher tool pelo texto de schema memorizado, seguir instrução só em template familiar — e degrada capacidade geral (queda de 7.7 pontos em IFEval).
  3. Formulação (seção 3.1): política πθ(a|x, h) com h ∈ H evoluindo no tempo (h_t no treino, h_{t+1}, h_{t+2}, … em produção). Objetivo duplo: efetividade sob um envelope de mudança de deploy mais amplo que qualquer snapshot de treino, e retenção de capacidade geral pós-fine-tuning.
  4. Harness-State Augmentation (seção 3.2): perturbações que preservam a tarefa ao longo de cinco dimensões — Skill Identifier (renomear, mascarear subconjuntos, injetar skills sintéticas plausíveis e de ruído, reescrever descrições por LLM forte), Skill Content (parafrasear regras, mascarear, reordenar), Tool Definition (renomear tools, reescrever descrições mantendo a função), System Prompt (reordenar blocos e itens, perturbar limites numéricos dentro de faixas operacionalmente válidas), Hook (variantes controladas de retry, estrutura de mensagem, modificações disparadas por hook). A hipótese: mudar a superfície torna atalhos nominais inúteis e força o roteamento pela informação funcional.
  5. Pipeline de três estágios (seção 3.4): (1) HSA-SFT — o compacto aprende de trajetórias filtradas geradas por teacher forte em ambientes HSA-diversificados; (2) General OPD — distilação on-policy do próprio modelo base em dados de domínio geral para recuperar a generalização que o SFT de domínio corrói; (3) HSA-RL — RL em ambiente simulado com harnesses aumentados; juízes penalizam invocação de tool que a augmentação removeu, seleção de skill inexistente, e violação de prompt modificado, e premiam a adaptação correta.
  6. Simulador on-policy (seção 3.3): réplica production-informed da live — inputs amostrados de cenários (dúvida de produto, chat casual, intenção de compra, pós-venda, misto) com estado de sala simulado, executores de tool, hooks, e interação multi-round limitada. A motivação: dados offline de teacher só contêm o caminho ótimo; o modelo precisa experimentar o próprio erro (tool que retorna erro, hook que força retry, skill errada e recuperação) para aprender a navegar o loop.

Evidência e resultados

Quatro suites complementares, > 4.500 casos. Live-Stream QA: 94.8 (base 80.3, melhor LLM geral 93.0). Harness-Variant QA: 94.6 (base 75.4) — robustez a variações do próprio harness. IFEval: 83.5, evitando a queda de 7.7 pontos que o Fixed-Harness SFT causa. Deployment real: agente completo em uma única NVIDIA H20 com MTP, P50 3.4s e P95 8.1s. A/B online no Taobao Live (produção): +4.33% GMV de recebimento confirmado e +0.91% item-page views, ambos UV-normalizados, contra controle ReAct. Pontos fortes do desenho: A/B de produção com métrica de negócio (não só bench), held-out harness edits avaliados separadamente (seção 5.6), judge calibrado contra anotação humana com protocolo às cegas (5.7), e análise de estabilidade bootstrap (C.4).

Limitações e riscos

Declarados pelo paper: o ganho central depende de treinar pesos (HAT é pipeline de treino), então quem consome modelo por API não captura o benefício; o OPD é um estágio extra cuja função é consertar dano que o próprio SFT causou — custo estrutural; o simulador é production-informed, mas simulado; o envelope E_deploy é especificado, perturbações fora dele (mudanças semânticas reais de quebra, não nominais) seguem descobertas. Suspeitados pela leitura: HSA ensina "siga a semântica, ignore a superfície" — desejável só quando a superfície é de fato irrelevante; um harness cujo rótulo carrega semântica (compliance, ids de tool que fazem coisas perigosas) não quer ser tratado como ruído. Os números de qualidade vêm de judge LLM calibrado, não de ground truth.

Teses transferíveis

  1. HSA como suíte de regressão de harness: rodar a mesma tarefa sob aliases de skill, schemas semanticamente equivalentes, reordenação de prompt e variantes de hook; se a execução quebra por mudança nominal, o contrato está mal especificado — o rótulo estava carregando a semântica que faltava na especificação.
  2. Gates textuais exigem perturbação auto-referencial na autoria: o comando do gate citado no relatório que ele audita não pode dispará-lo (propriedade auto-arquivável); gate que conta caractere solto em vez de par estrutural é acoplamento a superfície.
  3. Contratos estruturais pedem invariantes de consistência nominal, não só existência de campos: dois identificadores para o mesmo objeto (nome de diretório vs name de frontmatter) divergindo sem o gate notar é fragilidade de dispatch latente.
  4. Harness é distribuição versionada: toda promoção de mudança de harness é mudança de ambiente e exige re-run de regressão (o loop Diagnose → Confirm → Edit → Evaluate → Regression Check do paper é isso formalizado).
  5. O consumidor de saída de modelo também tem superfície: parse tolerante a variantes (fences, ruído ao redor, reordenação de chaves) é o análogo de HSA do lado de quem consome a saída — e o schema injetado no prompt merece snapshot, porque mudança de wording é perturbação silenciosa do contrato.

Veredito do paper

Vale destilar. Como técnica, é inaplicável ao nosso ecossistema (ninguém aqui treina pesos — e a parte honesta do destaque da edição está correta: o ganho principal mora no ajuste fino). Como diagnóstico e método de teste, é dos papéis mais transferíveis já destilados neste jornal: a inversão "harness como distribuição variável, não fixture fixa" muda a pergunta de avaliação de "passa?" para "passa sob perturbação nominal?". Recomendo o consumo via tese 1 como prática de regressão e tese 2 como convenção de autoria de gate.
