LoopArena: Benchmarking Models as Runtime Controllers for Loop Engineering

Sumário de ação: O padrão "Loop Contract" (registrar, a cada decisão de controle, qual obrigação operacional o controller assumiu antes de agir) é copiável como eixo de auditoria no workloop e no pipeline papers-deep, sem trocar modelo executor; o protocolo worker-fixo/controller-variável é o modelo para separar falha de orientação de falha de execução. Não adotar o ciclo de controle por rodada: o próprio paper mostra que controller custa até 9,4x o no-control e que restatement fixo de goal não melhora tarefa completa.

Afirmação central

Um modelo pode ser avaliado isoladamente como controller de um loop de coding agent — com o worker e o harness congelados — e essa habilidade é hoje gargalo e commodity ao mesmo tempo: em tarefas completas o melhor controller chega a 24,69% de Strict Success Rate contra 18,52% sem controle nenhum, enquanto repetir o objetivo deterministicamente a cada rodada (fixed control) empata com não controlar nada.

Mecânica passo a passo

Nota baseada em leitura completa do HTML (v1).

  1. Harness de dois papéis. O modelo avaliado é o Controller: sem ferramentas de código, sem acesso ao workspace. Um Worker fixo (Qwen3.7-Plus em todos os experimentos) executa a tarefa de código no seu loop ReAct nativo (inner loop); a orientação do Controller é o outer loop.
  2. Control cycle. Quando o Worker devolve o controle ao harness, o harness cria um Reporter temporário: mesmo modelo do Worker, cópia da conversa persistente, ferramentas read-only. O Reporter produz relatório em quatro partes (contexto da tarefa, trabalho feito e estado atual, evidência de verificação disponível, pendências), com claims materiais citando os turns do Worker que os suportam. Ele descreve estado; não decide próximo passo.
  3. Evidence Packet. O harness formata deterministicamente o relatório e os turns citados num packet estruturado, read-only — a única visão do run que o Controller recebe, além do seu próprio histórico de packets e contracts anteriores.
  4. Loop Contract. O Controller emite um contract estruturado: avançar (próximo segmento limitado do Worker, com condição explícita de retorno de controle), pedir verificação focada, ou parar. Se parar, o workspace vai ao avaliador. O contract é renderizado como o próximo prompt do Worker na conversa persistente.
  5. Três configurações de custo. Type I: uma decisão única — escolha 4-way entre contracts candidatos, com a resposta correta estabelecida durante a construção por replay duplo; avaliar um controller novo custa uma resposta por questão, zero execução do Worker. Type II: uma fatia da tarefa a partir de workspace intermediário preparado (o trabalho anterior dado como completo). Type III: a tarefa completa, do estado original.
  6. Construção do benchmark. 27 tarefas-fonte (11 do SCBench, 16 do BeyondSWE). Case Type II só vale se o workspace inicial falha ao menos um requisito novo do estágio e o estado-completo da fonte passa todos. Questão Type I só entra se um candidato é vencedor único, sob a mesma regra success-and-cost, em dois schedules de replay pré-declarados; candidatos e ordem congelados antes de qualquer replay. 90 questões Type I no total.
  7. Referências. No-control (o Worker recebe a tarefa uma vez e segue sozinho) e fixed-control (a cada handoff, o harness restata deterministicamente o objetivo original — inspirado no /goal do Codex; sem modelo, sem adaptação à evidência).
  8. Métricas. Contract Accuracy (Type I); Strict Success Rate (run conta como sucesso só se passa o avaliador E segue o protocolo; K=3 runs por tarefa por política); custo estimado de inferência por run (sem prompt caching, tabela de preços congelada, somando Worker+Reporter+Controller); Spearman ρ entre as ordenações Type II e Type III.

Evidência e resultados

Tabela 2 (27 tarefas × 3 runs; Worker fixo Qwen3.7-Plus; sucesso estrito = todos os Core checks no SCBench, reward 1 do avaliador Harbor no BeyondSWE):

| Política | Type I Acc. | Type II SSR / custo | Type III SSR / custo | |---|---|---|---| | No control | — | 39,51% / US$1,04 | 18,52% / US$2,01 | | Fixed control | — | 46,91% / US$1,08 | 18,52% / US$5,58 | | Qwen3.7-Plus | 72,22% | 48,15% / US$4,30 | 23,46% / US$6,89 | | DeepSeek-V4-Flash-0731 | 77,78% | 45,68% / US$2,10 | 19,75% / US$10,24 | | GLM 5.2 | 74,44% | 37,04% / US$1,63 | 16,05% / US$4,86 | | GPT-5.5 | 87,78% | 51,85% / US$5,00 | 24,69% / US$18,84 | | Claude Opus 4.8 | 76,67% | 48,15% / US$5,87 | 20,99% / US$16,82 |

  • O que os números valem: SSR estrita, painel de 5 controllers + 2 referências, um worker, dois benchmarks-fonte. GPT-5.5 soma +6,17pp sobre o no-control em Type III, pagando ~9,4x o custo por run. ρ(Type II, Type III)=0,9747 sob o critério Core: dos 9 pares de controllers estritamente ordenados em ambos, nenhum inverte; 1 de 10 pares contém empate. Redução de custo Type II vs Type III: média de 64,4% por controller, pareada. Type I: 72,22–87,78% com 0% de respostas inválidas; melhor atalho determinístico chega a 31,11% (chance uniforme: 25%).
  • O que os números NÃO significam: 24,69% não é "taxa de resolução de SWE-bench" nem comparação entre harnesses — é SSR num protocolo específico com avaliador estrito. 64,4% não é economia sobre o no-control (controllers custam MAIS que não controlar: US$4,86–18,84 vs US$2,01 em Type III); é a fatia vs a tarefa completa, pareada por controller. ρ=0,9747 vem de n=5 modelos — correlação alta com poucos pontos, sensibilidade a regras alternativas de scoring examinada só no apêndice. O custo assume zero prompt caching, o que infla exatamente o caso do controller (histórico reenviado a cada ciclo).
  • Nulos e como ler: fixed control = no-control em Type III (18,52% exatos, 81 runs cada) é informativo, não só subpotência: o empate exato com o contraste Type II (+7,40pp para fixed sobre no-control em fatia) suporta a leitura de que restatement de goal ajuda escopo curto e não substitui orientação adaptativa em escopo completo — e ainda custa 2,8x o no-control. GLM 5.2 em Type III fica ABAIXO do no-control (16,05% vs 18,52%): diferença de ~2 runs em 81, sem IC reportado — não dá para afirmar que o controller piora, mas o padrão custo/resultado é desfavorável (US$4,86 vs US$2,01).
  • Título vs evidência: "Models as Runtime Controllers" é entregue para 5 modelos frontier, 27 tarefas de código repo-level, 1 worker. Não é alegação sobre qualquer modelo, qualquer worker ou qualquer domínio — e o próprio §7 declara isso.

Limitações e riscos

Declaradas (§7): só código repo-level; só organização Controller-Worker com handoffs estruturados; multi-worker, outras famílias de worker e outros domínios ficam fora.

Suspeitadas na leitura: (a) o Reporter usa o mesmo modelo do Worker — o resumo que fundamenta cada decisão do controller é viésado pelo modelo que executou (e tem interesse narrativo na própria execução); (b) a "resposta correta" do Type I é correta sob uma regra success-and-cost com budget fixo em replay — é a resposta da regra, não verdade absoluta; (c) sem prompt caching, o custo do controller é superestimado relativo a produção real; (d) 27 tarefas / 5 modelos sem intervalos de confiança no corpo — ordenações estáveis, magnitudes frágeis; (e) a ordenação de controllers foi medida com um worker de classe média (Qwen3.7-Plus) — com worker mais capaz, o valor adicionado do controller pode encolher (o teto de 24,69% não diz nada sobre workers melhores).

Teses transferíveis

  1. Loop Contract como artefato de registro: a cada decisão de controle, registrar qual obrigação operacional o controller assumiu antes de agir (avançar/verificar/parar, com segmento limitado e condição de retorno). Isso dá um eixo de auditoria para dispatcher e skills de verificação sem trocar o modelo executor — quando o resultado final é ruim, o contrato gravado diz se a orientação prometeu a coisa errada.
  2. Protocolo worker-fixo/controller-variável: para avaliar qualquer camada de orquestração do ecossistema (dispatcher, prompt de comando, skill de verificação), congelar o executor e variar só a orientação. O agregado final de um run esconde se a falha foi de orientação ou de execução; o pareamento controlado expõe a diferença.
  3. Evidence Packet read-only com citações: decisões de controle sobre resumo estruturado produzido a partir de cópia da conversa do executor, com cada claim citando turn — nunca sobre memória do executor, nunca com acesso de escrita ao workspace. Barato e copiável como convenção de handoff.
  4. Ceticismo com goal-restatement: repetir o objetivo a cada rodada (estilo /goal) não melhora resultado em escopo completo (18,52% = no-control) e custa 2,8x mais. Orientação útil muda conforme o run migra entre implementação, verificação, recuperação e parada. Aplica-se a qualquer loop do ecossistema que "persista a meta" no lugar de ler o estado.
  5. Fatia como proxy barato de avaliação: parear a avaliação barata (fatia da tarefa) com a cara (tarefa completa) e validar com correlação de ordenação antes de confiar na barata — padrão direto para qualquer benchmark interno de agentes/skills.

Veredito do paper

Vale destilar e seguir. O desenho metodológico é o melhor do paper: isolar o controller como unidade avaliada, validar a resposta correta por replay duplo, parear fatia/tarefa-completa para medir o custo de avaliação. Os nulos são informativos (fixed control não substitui orientação adaptativa; controllers caros compram poucos pontos). Ressalvas: magnitudes valem para 27 tarefas/5 modelos/1 worker; o custo do controller é parte do resultado, não detalhe — e o custo relatado é pessimista (sem caching).

Confronto com repos

agent-workloops

  1. Teses aplicáveis — A Diretiva do workloop já é um parente de primeiro grau do Loop Contract: "o contrato de execução de UMA issue" (templates/diretiva.md:3), postada antes de qualquer código e executada só após aprovação nomeada (templates/diretiva.md:4). A diferença estrutural: no workloop o contrato é emitido uma vez por issue e congelado (templates/diretiva.md:10-11); no LoopArena, reemitido a cada control cycle com evidência fresca. O controle do modo lote é fixed-control determinístico por desenho: pick por "menor número ABERTO com todos os blockers CLOSED" (templates/runbook-loop.md:33-35), paradas imediatas declaradas a priori (templates/runbook-loop.md:55-67) — o controller adaptativo é o operador humano nos gates (playbooks/workloop.md:111). O resultado do paper (fixed control = no-control em Type III, 18,52%) NÃO condena esse desenho: o workloop não delega o julgamento adaptativo à política fixa, mantém-no no operador. Já o problema do stale progress note é tratado por convenção — "a próxima issue lê o handoff ANTES do plano... o plano é o que se pretendia; o handoff é o que aconteceu" (playbooks/workloop.md:218-219) — mas sem citação por turn nem checagem mecânica handoff↔diff; hoje isso é coberto caro pelo review adversarial (playbooks/workloop.md:200-205).
  2. Oportunidade de melhoria — Adicionar ao relatório de uma linha por issue (templates/runbook-loop.md:94-97) o campo "contrato assumido antes de agir": qual obrigação operacional a diretiva delegou e qual gate autorizou. Isso torna auditável, post hoc, o eixo central do paper — separar falha de orientação (diretiva ou aprovação errada) de falha de execução — sem adicionar ciclo de controle ao run.
  3. Como aplicar — Mudança de template apenas (seção 8 do runbook + cabeçalho da diretiva), sem código, retrocompatível com issues em andamento; validar na primeira execução de lote seguinte.
  4. Prós e contras — Pró: custo ~zero, ganho direto de auditabilidade do confrontos/ e do relatório de segmento. Contra: risco de burocratizar a linha de relatório. Não importar o ciclo controller-por-rodada do paper: o custo observado (controller até 9,4x o no-control em Type III) e a estrutura de gates humanos tornariam o ganho duvidoso aqui.
  5. Veredito — Aplicar com ressalvas: só o campo de registro de contrato no relatório; não o ciclo por rodada.

scripts

  1. Teses aplicáveis — O dispatch/preflight.sh já valida contrato ANTES da execução: gramática do bloco inteiro validada antes de rodar qualquer linha (dispatch/preflight.sh:41-69), allowlist por segmento com git read-only (dispatch/preflight.sh:16-17, 98-130), PIN de proveniência md5 contra sidecar (dispatch/preflight.sh:71-96). É o análogo mecânico do "contrato antes de agir" — mas pré-run e estático: não existe control cycle DURANTE o run, e a fronteira de sessão do dispatch encerra o controle quando a sessão termina. O caso de uso concreto das teses do paper é o próprio pipeline papers-deep: orquestrador (comando) + subagents executores é um par controller/worker real; a varredura pós-hoc do registro já existe e é read-only com classificação de drift (papers-deep/varre_registro.py:2-6, drift próprio vs externo em :84-86), e a atualização do registro é privilégio do orquestrador (:88-89).
  2. Oportunidade de melhoria — Registrar o Loop Contract de cada subagent do papers-deep (missão delegada + critério de verificação + condição de parada) no relatório que volta ao orquestrador, permitindo a auditoria orientação-vs-execução quando uma destilação sai ruim. Passo seguinte, opcional: avaliar o comando (controller) com subagent (worker) congelado — o protocolo worker-fixo do paper.
  3. Como aplicar — Primeiro como documentação do comando papers-deep (contrato por subagent), sem código; a avaliação comparativa com worker congelado é custo em execuções duplicadas de paper e só se justifica se a qualidade das destilações virar problema recorrente.
  4. Prós e contras — Pró: registro é barato e fecha a lacuna de auditabilidade entre o que o orquestrador pediu e o que o subagent devolveu. Contra: avaliação comparativa duplica custo de papers; e o preflight em si ganha pouco com o paper — já cobre o que o papel dele permite cobrir (pré-run). Não introduzir ciclo intra-run no dispatch: a fronteira de sessão é escolha de desenho deliberada do ecossistema, e o paper não a refuta (o control cycle dele é para tarefas de código longas, não para dispatch de spec pontual).
  5. Veredito — Aplicar com ressalvas: contrato registrado por subagent no pipeline papers-deep; sem ciclo de controle intra-run no dispatch.
