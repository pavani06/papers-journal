O dia foi útil para engenharia de agentes: autorização em memória, juízes frágeis e protocolos menos dependentes de prompt.

Os papers mais úteis hoje não foram os mais votados. O topo de popularidade ficou em simuladores educacionais, direção autônoma e arquitetura de modelo; para o teu sistema, o miolo importou mais: memória como política de autorização, confiabilidade de LLM-as-a-judge em tool-calling, separação entre protocolo e linguagem em multiagentes, e loops externos para desenvolvimento de software multi-dia.

O padrão do dia é bem alinhado com operação real: menos “modelo melhor” e mais “onde o harness mente para si mesmo”. Também apareceu bastante relatório de fundação — GUI agents, world models, multimodal unified models — mas poucos mudam uma decisão imediata. A ausência notável foi trabalho forte sobre observabilidade prática: muito benchmark e pouco tracing operacional reaproveitável.

Agent Memory Is a Surface for Endogenous Authorization Laundering

A afirmação importante é que memória não é só contexto: ela vira parte efetiva da política de autorização do agente. O modo de falha é interno, sem prompt injection externo: o escritor de memória registra uma permissão que o histórico não sustentava, e depois o executor age quase sempre sobre esse registro falso. O número é forte o suficiente para assustar: até 50,2% de falsas autoridades criadas nas atualizações incrementais, com 98,6% de execução quando a falsa autoridade já está presente.

Para o nosso casoNo teu sistema, permissões em memória deveriam virar event-sourced records com ponteiro obrigatório para evento-fonte, não resumos livres. Vale criar um gate que rejeite qualquer ação irreversível cuja autoridade venha apenas de memória condensada.

AgentJudgeBench: A Multi-Difficulty Benchmark for Evaluating LLM Judges on Agentic Tool-Calling

Este é um benchmark que vale porque revela um modo de falha, não porque ranqueia modelos. Em DAGs de tool-calling, juízes grandes convergem para uma faixa estreita em casos difíceis sem ground truth, sugerindo que escala não resolve a avaliação. O detalhe mais prático é que CoT e temperatura quase não ajudam; rubricas estruturadas ajudam um pouco, mas não generalizam uniformemente.

Para o nosso casoPara tua trilha de evidência, não trate judge frontier como verificador final de execução agentic. Use LLM judge como triagem, mas reserve ground truth, checks determinísticos ou rubricas específicas por workflow para gates que importam.

Control-Data Flow Separation: Stable Prompt Optimization in Multi-Agent LLMs

A tese é simples e diretamente operacional: prompts que misturam conteúdo da tarefa com routing, formato e sinais de parada são frágeis sob otimização. A separação proposta põe controle em objetos tipados e validados, deixando a linguagem livre apenas para o data flow. Isso ataca uma classe real de regressão em skills versionadas: uma melhoria textual que quebra contrato de execução.

Para o nosso casoVale auditar tuas skills e prompts para separar instrução semântica de protocolo de harness. Tudo que o código depende para dispatch, formato, stop condition ou handoff deveria ser schema validado, não texto negociável.

Harness-of-Harness: Multi-Day Autonomous Software Development with Continual Improvement

O interessante não é “agente escreve software”, é o papel do harness externo organizando iterações de planejamento, coding, teste e avaliação independente. A distinção entre teste usado durante implementação e avaliação separada é exatamente o tipo de separação que evita o agente otimizar para sua própria noção de pronto. O paper também reforça versioned project histories e incrementos pequenos, que são mais úteis que tentar prescrever a trajetória interna do agente.

Para o nosso casoAproveite como checklist de loop: incremento verificável, avaliação independente, histórico versionado e exposição progressiva de ferramentas/skills. Para um operador só, o ponto é reduzir superfície de revisão humana por incremento, não aumentar autonomia cega.
