Right Screen, Wrong Transition: World Models as Verifiers for GUI Agents

A afirmação central é que segurança em GUI não está no estado observado, mas na relação ação→próximo estado. A mesma tela de login pode ser legítima ou ataque dependendo do botão que a precedeu, então detectores que olham só para screenshot estão estruturalmente cegos. O ponto novo é o verificador prever diretamente a representação do próximo screen e comparar vetores, sem passar por uma segunda etapa generativa de julgamento.

Para o nosso casoNo seu harness, isso vira uma regra de desenho para monitores: logar e avaliar transições, não apenas estados finais. Para ações sensíveis, o gate deveria comparar a observação obtida contra uma expectativa condicionada pela ação declarada.

Cache Engineering for Agents

O paper separa context engineering textual de cache engineering: em vez de cortar ou resumir o prefixo e invalidar cache, o agente controla quais estados de KV continuam ativos. A parte importante para você não é implementar drop e repos amanhã — API comercial provavelmente não expõe isso — mas a noção de que duas conversas com tokens idênticos podem ter estados de cache diferentes. Isso quebra a suposição simples de que prefix matching basta para reutilização correta.

Para o nosso casoSe você versiona artefatos de contexto, trate operações sobre histórico como parte do estado executável, não como detalhe invisível. Quando provedores começarem a expor cache control, a trilha de evidência vai precisar registrar também operações de cache.

VerifierBench: Benchmarking the Generation of Executable Verifiers for LLM Agents

VerifierBench é um benchmark útil porque não apenas ranqueia modelos; ele mostra o modo de falha. Verifiers gerados rejeitam inválidos melhor do que aceitam válidos, e muitos falsos negativos vêm de suposições escondidas sobre formato, ferramenta ou mudança de código. O detalhe mais perigoso é que self-testing não pega isso quando o agente testa apenas soluções que compartilham a mesma suposição do verifier.

Para o nosso casoNo seu sistema, nenhum verifier gerado deveria ser aceito sem pelo menos um teste de aceitação com solução válida alternativa e um teste de diversidade de formato. Um gate simples é exigir evidência de que o verifier aceita alguma solução correta antes de usá-lo para bloquear execução.

Same Simulation, Different Evidence: Where Retrieved Tool Output Costs LLM Agents Accuracy

Este é pequeno em upvotes, mas muito perto do seu problema real. O agente roda a ferramenta corretamente, mas quando a saída longa fica fora da context window e é acessada por índice ou retrieval, alguns modelos respondem a partir de arquivos auxiliares mais convenientes e arredondam errado. O modo de falha é bom: não é incapacidade de computar, é substituição de evidência.

Para o nosso casoMarque explicitamente qual artefato é autoritativo para cada pergunta e faça o agente citar esse artefato antes de responder. Para tarefas com tool output longo, adicione um check de proveniência: a resposta deve apontar para o campo ou seção exata, não para um derivado intermediário.
